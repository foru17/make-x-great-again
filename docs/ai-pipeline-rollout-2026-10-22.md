## 真实流量发现与处置

首轮真实流量发现单账号批量传输的响应有明显解析失败，初始快照中单账号 HTTP 200 响应有 17 条解析失败；当时立即关闭批量，保留去重和真实计量。只接受单项原格式的解析兼容仍不足以证明恢复，因此再次临时关闭批量。

已实现的协议修正：**仅一个账号时直接使用原有单账号系统提示与输入协议，2–10 个账号才使用批量输入/ID协议；修复批次只剩一项时也复用原协议**。仍严格校验每个判定；多账号输出没有可核对 ID 时绝不猜测归属；修复最多一次，网络/HTTP错误不自动重复提交。

后续 10:47 UTC 起的一个窗口中，批量首尝试有 28 次有效响应、覆盖 36 个账号，同时有 15 次上游 HTTP 错误、1 次解析失败和 3 次处理中。该样本不足以认可批量稳定性，因此最终将批量开关设为 0；不在本轮继续反复部署试错。

发布期间还读到上游 HTTP 522/524/525。它们在临时单账号模式下也出现，不能把这些全部归因于批量、当作零消耗，或据此宣称上游故障已经修复。未修改供应商地址、模型或推理强度。

Cloudflare 明确说明，Worker 与唯一协调器的代码更新是最终一致的，短时间可能由新 Worker 调到旧协调器，通常持续秒到分钟。因此切换期同时出现 `classify` 与 `classify_batch`、以及旧格式失败时，不能仅凭控制面已显示新版本便认定全量请求都执行新代码。效果复查将按分钟拆分切换期和后续稳定窗口，不把首轮失败混成稳定效果。[官方说明](https://developers.cloudflare.com/durable-objects/platform/known-issues/#code-updates)

## 半小时复查与停止条件

读取当前部署、开关、health、管理员聚合和只读 D1 `model_usage`，核对：物理请求数、首尝试账号数、批次大小、真实输入/输出/总/推理/缓存 token、每账号 token、解析失败、第二次尝试、HTTP/unknown/started/缺失 usage、延迟分位数。按分钟看版本切换影响，以末段稳定窗口判断恢复。

旧系统没有准确的 token 基线，不能直接声称节省百分比；账号尝试也不是去重后的独立账号数。缺失和未知用量单独列出，推理与缓存是子集，不再加到总 token 中。后台 Agent 消耗不混入此次初筛优化效果。

若稳定窗口仍有明显解析失败或服务错误，复查任务通知维护者并建议回退，不自行发布。人工可通过一次保留变量的部署把 `AI_BATCH_ENABLED` 设为 0，保留去重和计量；必要时再关闭协调器。保留新 namespace 和用量表，不直接回滚/删除迁移或清空未知状态。
