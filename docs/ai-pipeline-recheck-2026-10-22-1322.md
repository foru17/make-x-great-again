## 请求为什么仍然多

1. 之前所谓“同账号去重”的准确范围是“同账号且完整模型输入相同的请求合并”。index.ts:2054 的 key 同时含 userPrompt(s)，其中上下文变化会产生不同 key；因此不能保证一个账号只调用一次。成功结果在 flight 中保留 60 秒。D1 账号结果另有状态 TTL，但这只能覆盖已经成功写入的判别。
2. classification-flight.ts 的普通错误结果只缓存 1000ms。model_http_error 属于这个分支，同一个输入一秒后再来就可能重新调用；这轮 42.54% 上游错误使此缺口更值得优先处理。模型层没有内部 HTTP 重试（这轮 attempt>1 为零），但无法据此排除用户后续请求对同账号重复尝试。
3. extension/lib/online-detection.ts 只保存成功判别，失败直接返回 failed，不保存账号失败冷却。content.ts 的正常账号/不确定账号缓存还依赖 signalsHash 相同，hash 含近期推文与触发文本，新文本会再次请求在线接口。即便边缘缓存拦住模型，也仍会增加在线 HTTP 请求。
4. AI_BATCH_ENABLED 当前仍为 0，所以没有运行“每批10账号、最多2秒”的合并；不能期待当前版本获得批量收益。解析验收之前应继续保持暂停。

以上是已读源码确认的机制，不是已经量化的重复账号比例。model_usage 没有账号指纹或去重命中结果，不能从现有流水还原唯一账号数、同账号失败重入次数或准确节省比例。contrib 是贡献/调用路径计数，不是全部在线 HTTP 请求，不能用来代替接口流量。当前健康、管理员三个接口、Cloudflare 版本与配置读取均200；版本仍为 be14d2ae-1ecc-414e-a0ce-3aa3c36d7270，去重和usage开关1，批量0。
